01

환경 준비 — Node.js 설치

JavaScript 실행 환경 · 최신 LTS(v22 이상)
Windows 10/11 · macOS 두 갈래 설치, 확인, 오류 해결

Node.js · 무엇인가

Node.js는 JavaScript 실행 환경입니다

next.js 실행에 필요합니다. 브라우저 밖(내 컴퓨터)에서 JavaScript를 돌려 주는 엔진이라고 생각하면 됩니다.

다운로드

https://nodejs.org/ko/download

공식 다운로드 페이지 하나면 충분합니다. (클릭하면 열립니다)

설치할 버전

Node.js LTS — v22 이상

다운로드 페이지에서 반드시 LTS 탭을 선택하세요. LTS(Long Term Support)는 장기 지원되는 안정 버전입니다.

함께 설치되는 것
Node.js를 설치하면 패키지 관리자 npm이 함께 설치됩니다. 뒤에서 npm --version으로 같이 확인합니다.
Windows 10/11 · 설치 ① 다운로드

LTS 탭 선택 → .msi 64-bit 다운로드

  1. 다운로드 링크 접속 → LTS 탭 선택
  2. Windows Installer (.msi) 64-bit 다운로드
Windows 10/11 · 설치 ② 마법사 시작

설치 파일 실행 → 라이선스 동의

  1. 다운로드한 설치 파일(.msi) 실행
  2. 라이선스 동의 체크 → Next 반복
Windows 10/11 · 설치 ③ 기본 설정 유지

설정은 전부 기본값 그대로 Next

설치 경로, 구성 요소, Native Tools 화면 모두 손대지 않고 Next만 누르면 됩니다.

Windows 10/11 · 설치 ④ 설치와 완료

Install 클릭 → 권한 허용 → Finish

  1. 기본 설정 유지 → Install 클릭 (사용자 계정 컨트롤이 뜨면 예)
  2. 설치 완료 후 Finish
macOS · 방법 1

공식 설치 프로그램 (.pkg)

  1. 다운로드 링크 접속 → LTS 탭 선택
  2. macOS Installer (.pkg) 다운로드
  3. .pkg 파일 실행 → 계속 → 설치 → 완료
Tip
Windows의 .msi와 마찬가지로, 중간 설정은 전부 기본값 그대로 진행하면 됩니다.
macOS · 방법 2

Homebrew 한 줄 설치

Homebrew(맥용 패키지 관리자)를 이미 쓰고 있다면 터미널 한 줄이 가장 빠릅니다.

# 터미널에서 아래 명령어 입력
brew install node
둘 중 무엇을 쓰나
Homebrew가 뭔지 모른다면 방법 1(.pkg 설치 프로그램)을 쓰세요. 결과는 동일합니다.
설치 확인 · ✅

터미널을 새로 연 뒤 버전을 확인합니다

터미널을 닫고 새로 연 뒤, 아래 명령어를 하나씩 입력하세요.

node --version
npm --version

예상 출력 — node

v22.x.x 이상 (LTS 버전)

예상 출력 — npm

10.x.x 이상

왜 새로 여나요
설치가 등록한 경로(PATH)는 새 터미널부터 적용됩니다. 기존 창에서는 명령을 못 찾을 수 있습니다.
오류 해결 ① · ❌

node 입력 시 command not found

원인

Node.js PATH 미등록 — 시스템이 node 명령의 위치를 모르는 상태입니다.

해결

  • 터미널을 닫고 새로 열어보기
  • 그래도 안 되면 Node.js 재설치
오류 해결 ② · ❌ Windows 11

npm -v 입력 시 PSSecurityException

Node.js를 설치했는데 PowerShell에서 npm -v를 입력하면 PSSecurityException 오류가 발생하는 경우가 있습니다.

원인
명령어를 찾긴 찾았지만, PowerShell의 보안 정책이 npm 스크립트(npm.ps1)의 실행을 막고 있는 것입니다. 설치가 잘못된 게 아닙니다.
오류 해결 ② · 조치

PowerShell 실행 정책 변경 (관리자 권한 필요)

  1. PowerShell을 관리자 권한으로 실행
    Win 키 → PowerShell 검색 → 앱 우클릭 → 관리자 권한으로 실행
  2. 아래 명령어 입력 후 Enter
    Set-ExecutionPolicy RemoteSigned
  3. 변경 확인 메시지에서 Y 입력 후 Enter
  4. 같은 창(또는 새 PowerShell)에서 재확인
    npm -v
참고 · RemoteSigned란

RemoteSigned는 위험한 설정이 아닙니다

로컬 스크립트는 허용하고, 인터넷에서 다운로드한 스크립트는 서명된 경우만 실행하도록 하는 일반적인 개발자 설정입니다.

Part 1 완료 체크리스트
  • node --version → v22.x.x 이상 출력
  • npm --version → 10.x.x 이상 출력
  • Windows 11에서 PSSecurityException이 났다면 → RemoteSigned 적용 후 재확인
02

git / github — 옷장과 창고로 이해하기

비개발자를 위한 완전 입문
코드를 한 줄도 몰라도 됩니다. “계절이 바뀔 때 옷을 정리해 창고에 맡기는 일”에 빗대어, 개발자들이 하루에도 수십 번 쓰는 여섯 개의 명령어를 이해합니다.

준비물 — git 설치: git-scm.com/downloads · GitHub 가입: github.com (클릭하면 열립니다)

시작하기 전

우리는 이미 이 문제를 겪고 있다

한 번쯤 이런 폴더를 본 적이 있을 겁니다.

제안서.docx 제안서_수정.docx 제안서_최종.docx 제안서_최종_진짜최종.docx 제안서_최종_진짜최종_김부장님피드백반영.docx
시작하기 전

이 방식은 세 지점에서 반드시 무너집니다

1

무엇이 달라졌는지
알 수 없다

파일 두 개를 열어놓고 눈으로 비교하는 수밖에 없습니다.
2

되돌릴 수 없다

“3일 전 버전이 더 나았는데” 싶어도, 그 사이에 덮어썼다면 끝입니다.
3

동시에 고치면
하나가 사라진다

각자 고친 파일을 주고받다 보면 누군가의 작업은 반드시 날아갑니다.
그래서
git은 정확히 이 세 가지를 해결하려고 만들어진 도구입니다. 그리고 github는 그 결과물을 여러 사람이 함께 쓰도록 인터넷에 올려두는 서비스입니다.
핵심 한 문장

git은 “무엇을, 언제, 왜 바꿨는지”를 기록으로 남기고
언제든 그 시점으로 되돌아갈 수 있게 해주는 도구입니다.

가장 먼저 짚을 구분

git과 github는 다른 것입니다

🏠 git — 우리 집 거실의 작업대

옷을 꺼내 늘어놓고, 고르고, 박스에 담고, 이름표를 붙이는 모든 작업이 여기서 일어납니다. 내 컴퓨터 안에서만 돌아가기 때문에 인터넷이 끊겨도 상관없습니다.

🏢 github — 동네 물류 창고 회사

포장이 끝난 박스를 맡아두고, 가족이든 동료든 허락된 사람이라면 누구나 같은 창고에서 박스를 꺼내 볼 수 있게 해줍니다. 창고에 보내려면 당연히 인터넷이 필요합니다.

단계 1 / 6

git init — 작업대를 편다

옷장 비유
계절이 바뀌었습니다. 옷 정리를 시작하려면 먼저 거실 한가운데에 큰 작업대를 펴야 합니다. 작업대를 펴기 전까지는 옷을 아무리 옮겨도 아무도 기억해주지 않습니다.

git init은 “이 폴더에서 벌어지는 모든 변화를 이제부터 기록하겠다”고 선언하는 단 한 번의 행위입니다. 실행하면 폴더 안에 작은 관리 공간(“작업대 밑 기록 서랍”)이 생기고, 앞으로의 모든 기록이 거기 쌓입니다. 직접 열어볼 일은 거의 없습니다.

git init
📌 언제 하나요
프로젝트를 처음 시작할 때 딱 한 번만 합니다. 이미 작업대가 펴진 폴더에 다시 할 필요 없고, git clone으로 가져온 폴더에는 작업대가 이미 펴져 있으므로 하지 않습니다.
단계 2 / 6

git add — 보낼 옷을 골라낸다

옷장 비유
옷장엔 겨울옷·여름옷·아이 옷·버릴 옷이 뒤섞여 있습니다. “이번에 창고로 보낼 건 아빠 겨울옷만”이라면, 옷장 전체가 아니라 그것만 골라 작업대 옆 바닥 — 포장 대기 구역 — 에 쌓아둡니다.

git add는 바꾼 것들 중 이번 기록에 포함시킬 것만 골라내는 작업입니다.

왜 이런 단계가 따로 있지?
하루에도 여러 일을 동시에 건드리기 때문입니다. 오전엔 계약서 문구, 오후엔 표지 디자인 — 한 박스에 뒤섞으면 “표지만 예전으로 되돌리고 싶을 때” 손쓸 수 없습니다. 골라 담는 단계가 있어야 기록의 단위를 내가 정할 수 있습니다.
단계 2 / 6 · 사용법

git add — 두 가지 쓰임새

git add 파일이름   # 특정 파일 하나만 고른다
git add .         # 점 하나 = "바뀐 것 전부 다"

익숙해지기 전까지는 점 하나로 전부 담는 습관이 편하지만, 기록을 깔끔하게 남기고 싶다면 골라 담는 쪽이 훨씬 낫습니다.

📌 꼭 기억할 것
git add를 했다고 아직 아무것도 저장되지 않았습니다. 옷을 바닥에 쌓아만 둔 상태라, 마음이 바뀌면 그냥 도로 옷장에 넣으면 됩니다. 되돌리기가 가장 쉬운 단계입니다.
단계 3 / 6

git commit — 박스를 봉하고 이름표를 붙인다

옷장 비유
바닥의 아빠 겨울옷을 박스에 담아 테이프로 봉하고, 매직으로 큼직하게 씁니다. “겨울 아빠옷”. 이 순간 박스는 하나의 완결된 덩어리가 되고, 동시에 언제든 다시 찾아올 수 있는 시점이 됩니다.

git commit은 골라둔 변경사항을 하나의 기록으로 확정 짓는 행위입니다. git에서 가장 중요한 명령어이고, 사실상 git의 존재 이유이기도 합니다.

git commit -m "겨울 아빠옷"

-m 뒤 따옴표 문장이 바로 박스에 쓰는 이름표 — 정식 명칭은 커밋 메시지입니다.

단계 3 / 6 · 커밋 메시지

이름표를 잘 쓰는 것이 절반입니다

3개월 뒤의 나는 오늘의 나를 전혀 기억하지 못합니다. 창고에 박스 200개가 전부 “정리함”, “수정”, “ㅇㅇ”이라면 그 기록은 없는 것과 같습니다.

나쁜 이름표좋은 이름표왜
수정계약서 3조 위약금 조항 문구 수정무엇을 바꿨는지 보인다
ㅇㅇ표지 이미지를 저해상도에서 원본으로 교체찾아올 이유가 생긴다
최종고객사 피드백 반영 — 가격표 페이지 추가맥락이 남는다
중간 점검

여기까지는 전부 내 컴퓨터 안의 일입니다

📌 기억하세요
init · add · commit 세 단계는 전부 우리 집 거실에서 벌어지는 일입니다. 인터넷이 끊긴 비행기 안에서도 얼마든지 할 수 있습니다. 아직 창고는 우리가 뭘 했는지 전혀 모릅니다.

🧩 git status

지금 작업대 상태를 확인하는 명령. 어떤 옷이 바닥에 나와 있고 어떤 옷이 아직 옷장에 있는지 보여줍니다. 헷갈릴 때마다 부담 없이 쳐보면 됩니다.

🧩 git log

지금까지 봉한 박스 목록을 보는 명령. 이름표가 최근 순으로 쭉 나옵니다.

단계 4 / 6

git push — 창고로 박스를 보낸다

옷장 비유
봉인된 박스를 트럭에 실어 동네 창고로 보냅니다. 이제 우리 집에 불이 나도, 노트북이 고장 나도 창고에는 박스가 남아 있습니다. 창고 이용 권한이 있는 가족이라면 누구나 그 박스를 열어볼 수 있습니다.

역할 1 — 백업

내 컴퓨터가 사라져도 기록은 남습니다.

역할 2 — 공유

이 순간부터 팀원들이 내 작업을 볼 수 있게 됩니다.
git push
📌 push는 commit을 대신하지 않습니다
봉하지 않은 박스는 트럭에 실리지 않습니다. commit하지 않은 변경사항은 push해도 창고로 가지 않습니다. 순서는 언제나 고르고(add) → 봉하고(commit) → 보낸다(push) 입니다.
단계 5 / 6

git pull — 계절이 돌아와 박스를 가져온다

옷장 비유
다시 겨울이 왔습니다. 창고의 박스를 가져와 작업대에 풉니다. 그런데 그 사이 다른 가족이 창고에 새 박스를 넣어뒀을 수도 있습니다. 아내가 여름 동안 아이 옷을 정리해 보냈다면, 내가 가져오는 순간 그 박스도 함께 딸려옵니다.

git pull은 창고의 최신 상태를 내 작업대로 내려받는 작업입니다. 혼자 일할 때는 “다른 컴퓨터에서 하던 작업 이어받기”, 여럿이 일할 때는 “동료들이 그 사이 한 작업을 내 쪽에 반영하기” — 후자가 훨씬 중요합니다.

git pull
⏰ 습관으로 만들면 좋은 타이밍
일을 시작하기 전에 먼저 git pull — 이 습관 하나로 대부분의 골치 아픈 상황을 예방합니다. 몇 달 전 옷장을 붙들고 정리하는데 창고는 이미 딴판인 상황이 가장 곤란합니다.
단계 6 / 6

git clone — 다른 집에서도 같은 창고를 쓴다

옷장 비유
회사에 새 동료가 왔습니다. 처음부터 옷을 하나하나 옮길 필요 없이 창고 주소와 출입 권한만 건네주면, 그 사람이 박스를 통째로 받아 자기 집 거실에 작업대를 펴고 옷장을 그대로 복원합니다.

git clone은 창고의 프로젝트 전체를 통째로 내 컴퓨터에 처음 가져오는 작업입니다. 현재 상태만이 아니라 지금까지 쌓인 모든 박스 — 전체 기록이 함께 옵니다. 그래서 받은 직후부터 “3개월 전으로 되돌리기”가 바로 가능합니다.

git clone 창고주소
🔁 clone과 pull은 어떻게 다른가요
clone = 처음 한 번, 아무것도 없는 상태에서 통째로. 이사 들어오는 날 하는 일.
pull = 이미 옷장이 있는 상태에서 바뀐 것만. 매일 아침 하는 일.
브랜치 · 왜 필요한가

실험과 일상은 충돌합니다

상황
우리 집 옷장은 온 가족이 매일 씁니다. 아침마다 아빠는 셔츠를, 아이는 체육복을 꺼내 입습니다. 그런데 문득 — “계절별 말고 사람별로 나눠보면 훨씬 낫지 않을까?”

좋은 아이디어지만, 실험하려면 옷장을 전부 헤집어야 합니다. 서랍을 다 빼는 순간 가족들은 내일 아침 입을 옷을 찾지 못합니다. 반쯤 해보고 “역시 아니네” 싶어도 되돌리는 데 또 하루가 걸립니다.

이게 브랜치가 없을 때 벌어지는 일이고, 이 딜레마는 일에서 매일 반복됩니다.

  • 새 기능을 만들어보고 싶은데, 만드는 동안 서비스가 망가져 있으면 안 된다.
  • 문서 구조를 대대적으로 바꾸고 싶은데, 그 사이에도 다른 사람은 기존 문서를 봐야 한다.
  • 두 사람이 각자 다른 구역을 동시에 정리하고 싶은데, 옷장은 하나뿐이다.
브랜치가 해결하는 문제 · 🎯

“멀쩡히 돌아가는 것을 건드리지 않으면서,
마음껏 실험하고 싶다.”

이 한 문장이 브랜치가 존재하는 이유 전부입니다.

브랜치 · 무엇인가

어느 시점에서 갈라져 나온 또 하나의 작업 줄기

해결책
지금 이 순간의 옷장을 통째로 복사해 실험용 옷장을 하나 더 만듭니다. 가족들은 원래 옷장을 그대로 쓰고, 나는 실험용 옷장에서만 서랍을 빼고 늘어놓습니다. 실험용 옷장에서도 하는 일은 똑같습니다 — 고르고(add), 봉하고(commit), 보냅니다(push). 다만 그 기록은 실험용 옷장의 기록으로만 쌓입니다. 실험이 성공하면 원래 옷장에 반영하고, 실패하면 통째로 버립니다. 원래 옷장은 처음부터 끝까지 멀쩡합니다.
옷장 비유git 용어성격
가족이 매일 쓰는 원래 옷장main 브랜치항상 정상이어야 하는 기준선
실험용으로 하나 더 만든 옷장새로 만든 브랜치망가져도 되는 작업 공간
실험 결과를 원래 옷장에 반영병합, merge실험이 성공했을 때만
브랜치 · 그림으로

갈라졌다가, 성공하면 합쳐진다

main · 1월계절별 정리
→
main · 2월아이 옷 추가
→
main · 4월실험 결과 반영 완료
↘ 갈라져 나옴
실험 브랜치사람별로 재배치
→
실험 브랜치라벨 정리
↗ 합치기(merge)
🪄 옷장을 복사하면 공간이 두 배로 드나요?
비유상으로는 그렇지만 실제로는 아닙니다. git은 갈라진 이후 달라진 부분만 기록합니다. 브랜치 열 개를 만들어도 저장 공간은 거의 늘지 않고 만드는 시간도 순식간 — 브랜치를 아끼면서 쓸 이유가 전혀 없습니다.
브랜치 · 실전 명령

실제로는 이렇게 씁니다

git switch -c 사람별-정리-실험   # 실험용 옷장을 만들고 그 앞에 서는 것까지 한 번에

git add .
git commit -m "아빠 서랍과 아이 서랍 분리"
git push                        # 이후는 배운 것과 완전히 똑같이

git switch main                 # 원래 옷장 앞으로 돌아가기
git merge 사람별-정리-실험       # 실험이 성공했다면 원래 옷장에 반영
놀라지 마세요
git switch main 하는 순간 폴더 내용물이 원래 옷장 상태로 통째로 되돌아갑니다. 파일이 사라진 게 아니라 다른 옷장 앞에 서 있는 것뿐입니다. 다시 git switch 사람별-정리-실험 하면 그대로 돌아옵니다.
브랜치 · 충돌

같은 서랍을 둘이 다르게 바꿨다면 — 충돌

🤝 상황
나는 실험용 옷장에서 3번 서랍을 아이 옷으로 채웠는데, 그 사이 다른 가족이 원래 옷장의 3번 서랍을 겨울 이불로 채웠다면 — git은 어느 쪽이 맞는지 스스로 판단하지 않습니다. 대신 “여기 두 가지 버전이 있으니 직접 골라주세요” 하고 멈춰 섭니다. 이것이 충돌(conflict)입니다.

무서운 상황이 아니라, git이 조용히 덮어쓰지 않고 물어봐 주는 가장 안전한 동작입니다.
사람이 보고 결정한 뒤 다시 봉하면 끝납니다.

브랜치 · 도입 시기

이 개념, 언제 알아보면 되나요

아직 몰라도 되는 시기

혼자서, 하나의 폴더를, 순서대로만 고치고 있을 때. add · commit · push · pull 네 개면 충분합니다. 브랜치를 억지로 끼워 넣으면 오히려 헷갈립니다.

슬슬 알아볼 시기

“이거 한번 갈아엎어 보고 싶은데 지금 잘 돌아가는 걸 망칠까 봐 못 하겠다”는 생각이 처음 들었을 때. 이 감정이 곧 브랜치가 필요하다는 신호입니다.

반드시 써야 할 시기

나 말고 다른 사람이 같은 프로젝트를 건드리기 시작한 순간. 이때부터 브랜치 없이 일하는 것은 옷장 하나를 두고 두 사람이 동시에 정리하는 것과 같습니다.

한 계절을 통째로 복습하기

하나의 이야기로 이어 붙이면

  1. 거실에 작업대를 편다. 이제부터 전부 기록. git init
  2. 아침에 창고에서 최신 박스를 받아온다. git pull
  3. 큰 실험이라면 실험용 옷장을 만든다. git switch -c 브랜치이름
  4. 보낼 옷을 골라 바닥에 쌓는다. git add
  1. 박스를 봉하고 이름표를 쓴다. git commit -m "겨울 아빠옷"
  2. 박스를 창고로 보낸다. 백업이자 공유. git push
  3. 실험이 성공했다면 반영, 실패라면 폐기. git merge
  4. 다른 집에도 같은 창고를. 주소만 건네면 됨. git clone
🌱 딱 하나만 가져가신다면
commit은 되돌아올 수 있는 지점을 만드는 일입니다. 자주, 작게, 이름표를 잘 써서 남기는 습관 하나만 들여도 git이 주는 이득의 대부분을 가져갈 수 있습니다. 나머지는 그 위에 얹히는 편의 기능입니다.

기능 1 / 5 · AGENTS.md

AGENTS.md — 모든 것의 기준점 공식 문서 → agents-md

역할 — Codex가 작업 시작 전에 읽는, 저장소의 지속적인 자연어 지침. OpenAI 공식 정의는 “Codex에 추가 지침과 프로젝트 맥락을 제공하는 파일”입니다.

왜 필요한가 — 관계 관점
나머지 네 기능은 모두 AGENTS.md가 세운 방향 위에서 작동합니다. Memory는 못 담는 과거의 맥락을, Skills는 다 넣으면 터지는 상세 절차를, Rules와 Hooks는 강제력의 한계를 보완합니다. 즉 AGENTS.md가 없으면 나머지 넷은 보완할 기준 자체가 없어집니다.
AGENTS.md만 있으면 어떻게 되나
매 세션 처음부터 설명하는 반복은 없어지지만 — 기억도, 강제도, 자동 검증도 없는 “문서만 있는 팀”이 됩니다.
기능 1 / 5 · AGENTS.md 사용법

어디에 두고, 어떤 순서로 읽히나

  • 전역: ~/.codex/AGENTS.md — 모든 프로젝트 공통 개인 선호
  • 임시 대체: ~/.codex/AGENTS.override.md — 같은 위치의 기본 파일보다 우선
  • 프로젝트: 저장소 루트 → 현재 작업 디렉터리 순으로 계층적으로 읽고 합침 — 가까운 파일이 더 구체적인 지침으로 작동, 기본 최대 32KiB
  • 각 디렉터리에서 확인 순서: AGENTS.override.md → AGENTS.md → 설정에 등록한 대체 파일명
기능 1 / 5 · AGENTS.md 예시와 한계

작게 유지하고, 겪은 실수를 쌓아가기

# AGENTS.md (예시)
## 개발 규칙
- 패키지 관리자는 pnpm을 사용한다.
- API 응답 타입에 any를 사용하지 않는다.
## 검증
- 코드 수정 후 pnpm lint / typecheck / test 실행
## 주의사항
- 승인 없이 새 프로덕션 의존성을 추가하지 않는다.

적합한 내용

빌드·테스트 명령, 코드 스타일, 폴더 구조, 자주 발생하는 실수, PR 검토 기준, 변경 금지 영역, 작업 완료 조건.
OpenAI 권장: 작게 유지하고, 반복되는 리뷰 피드백과 잘못된 가정을 추가하며 발전시키기.

한계
자연어 지침이라 기술적 차단 장치가 아닙니다. “rm -rf 하지 마”라고 적어도 모델이 어기면 그만. 반드시 막을 명령은 Rules로, 반드시 실행될 검증은 Hooks나 CI로.
기능 2 / 5 · Memory

Memory — AGENTS.md가 못 담는 “시간”을 보충 공식 문서 → memories

역할 — 이전 대화에서 다음 작업에도 유용할 정보(선호 작업 방식, 과거 결정, 반복 사용한 명령, 구조 선택 이유)를 추출해 ~/.codex/memories/에 자동 저장하고 새 세션에 주입하는 공식 기능. 파일은 자동 생성 상태로 취급되며 직접 편집이 기본 제어 방식이 아닙니다.

왜 필요한가 — 관계 관점
AGENTS.md는 사람이 손으로 관리하는 정적 문서입니다. “지난주에 이 구조를 왜 선택했는지”, “저번에 어떤 테스트 명령을 썼는지”를 매번 손으로 옮겨 적는 건 현실적으로 불가능합니다. Memory는 이 시간 축의 빈틈을 자동으로 메웁니다.

AGENTS.md가 헌법이라면, Memory는 업무 일지입니다.

기능 2 / 5 · Memory 한계와 사용법

Memory는 정책 저장소가 아닙니다

한계 — 역방향 관계
Memory는 “도움이 되는 기억”이지 반드시 적용되는 정책 저장소가 아닙니다. 짧은 세션은 건너뛸 수 있고, 사용량 한도에 가까우면 생성이 생략될 수 있으며, 주입 여부도 설정에 따릅니다. 그래서 — 필수 규칙(운영 DB 직접 수정 금지, 테스트 통과 필수 등)은 Memory가 아니라 AGENTS.md에 둬야 합니다. OpenAI도 필수 팀 지침은 AGENTS.md나 저장소 문서에, Memory는 보조 회상 계층으로 안내합니다.
  • 기본 꺼짐 — 활성화: 앱 Settings → Personalization → Enable memories
  • 대화별 제어는 /memories
  • ChatGPT 계정 Memory와 로컬 Codex Memory는 별개. 비밀 값은 생성 메모리에서 제거되도록 설계.
# config.toml
[features]
memories = true

[memories]
# 현재 대화를 향후 메모리 생성에 사용
generate_memories = true
# 기존 메모리를 새 세션에 주입
use_memories = true
# MCP·웹 검색 사용 대화는 생성 제외
disable_on_external_context = true
기능 3 / 5 · Skills

Skills — 다 넣으면 안 되는 “깊이”를 분리 공식 문서 → build-skills

역할 — 지침·스크립트·참고 문서·자산을 폴더 하나로 묶은 재사용 워크플로 패키지. 필수 파일은 SKILL.md 하나(메타데이터 name, description 필수).

왜 필요한가 — 관계 관점
AGENTS.md는 항상 읽힙니다(합산 최대 32KiB). PR 리뷰 절차 5단계, 배포 체크리스트, 데이터 마이그레이션 절차를 전부 넣으면 매 요청마다 그 전부가 컨텍스트를 차지하고 곧 크기 한계에 부딪힙니다. Skills는 Progressive Disclosure로 이 문제를 풉니다.
  1. 평소에는 각 Skill의 name, description만 로드
  2. 해당 Skill이 선택되면 그때 SKILL.md 전체를 읽음
  3. 참고 문서·스크립트는 필요할 때만 사용
기능 3 / 5 · Skills 구조와 호출

폴더 구조 · 위치 · 호출 방법

my-skill/
├── SKILL.md          # 필수 (name, description)
├── scripts/          # 실행 가능한 자동화 코드 (선택)
├── references/       # 참고 문서 (선택)
├── assets/           # 템플릿·리소스 (선택)
└── agents/openai.yaml # 표시 이름·호출 정책·MCP 의존성 (선택)
  • 개인 전역: ~/.agents/skills/ · 저장소: <repo>/.agents/skills/ (현재 디렉터리→저장소 루트로 탐색)
  • 주의 — AGENTS.md는 ~/.codex/, Skills는 ~/.agents/. 위치가 다릅니다.
  • 명시적 호출 — 앱에서 @review-pr, CLI에서 /skills 또는 $review-pr
  • 암시적 호출 — 요청이 description과 일치하면 자동 선택
핵심 구분
“항상 알아야 할 것”은 AGENTS.md, “특정 업무를 할 때만 알아야 할 것”은 Skill. 이 분리 덕분에 상세 절차를 아무리 많이 보유해도 기본 컨텍스트가 비대해지지 않습니다.
기능 3 / 5 · description과 배포

그래서 description이 중요합니다

❌ 나쁜 description

“개발 작업을 돕는다”

언제 골라야 할지 알 수 없음 → 암시적 호출이 작동하지 않음

✅ 좋은 description

“사용자가 PR 검토, 코드 리뷰, 회귀 분석, 테스트 누락 검사를 요청할 때 사용”

요청 문장과 매칭될 단서가 풍부함

배포 관계
Skill = 워크플로 작성 형식 · Plugin = Skill+Connector 배포 단위 · MCP = 외부 서비스 연결 방식. 여러 사람에게 배포하려면 Plugin으로 패키징 권장. 또한 Skill은 “절차 지식” 자체를 담으므로, 팀에 배포하면 사람마다 다르게 시키던 업무가 표준화됩니다.
기능 4 / 5 · Rules

Rules — 자연어 지침의 “강제력” 한계를 메움 공식 문서 → rules

역할 — Codex가 샌드박스 바깥에서 실행하려는 명령을 allow(허용) / prompt(사용자 승인 요청) / forbidden(금지)으로 통제하는 실행 정책. 파일명은 rules.md가 아니라 ~/.codex/rules/default.rules 같은 *.rules 파일이며, 현재 실험적 기능입니다.

왜 필요한가 — 관계 관점
AGENTS.md에 “위험한 명령 쓰지 마”라고 적는 것은 부탁입니다. 모델이 지시를 오해하거나, 컨텍스트가 밀려나거나, 프롬프트 인젝션을 당하면 부탁은 지켜지지 않을 수 있습니다. Rules는 같은 요구를 모델 바깥의 정책 계층으로 옮깁니다. 모델이 무엇을 생각하든, forbidden에 걸린 명령은 실행 자체가 차단됩니다.

즉 Rules는 AGENTS.md의 대체재가 아니라, 그 문장 중 “어겨서는 안 되는 것”만 골라 강제 계층으로 승격시키는 장치입니다.

기능 4 / 5 · Rules 사용법

prefix_rule() — 이렇게 씁니다

prefix_rule(
    pattern = ["gh", "pr", "view"],
    decision = "prompt",
    justification = "GitHub PR 조회는
      사용자 승인 후 실행",
)

prefix_rule(
    pattern = ["rm", "-rf"],
    decision = "forbidden",
    justification = "재귀적 강제 삭제 금지",
)
  • 위치: ~/.codex/rules/ 또는 신뢰된 프로젝트의 <repo>/.codex/rules/
  • 여러 규칙이 동시에 일치하면 더 제한적인 결정이 승리:
    forbidden > prompt > allow
  • Codex는 시작 시 활성 설정 계층의 rules/ 폴더를 스캔
  • TUI에서 명령을 허용 목록에 추가하면 ~/.codex/rules/default.rules에 기록될 수 있음
기능 5 / 5 · Hooks

Hooks — 지침을 “실행”으로 바꾸는 장치 공식 문서 → hooks

역할 — Codex 생명주기의 특정 시점(세션 시작, 도구 실행 전후, 턴 종료 등)에 결정론적인 사용자 스크립트를 실행하는 공식 확장 프레임워크.

왜 필요한가 — 관계 관점
AGENTS.md에 “수정 후 린트 실행해라”라고 적으면 모델이 대체로 실행하지만 바쁜 턴에서는 빼먹을 수 있습니다. Rules는 명령을 막을 수는 있어도 무언가를 실행시킬 수는 없습니다. Hooks가 이 마지막 빈틈을 채웁니다 — “정해진 순간에, 모델의 판단과 무관하게, 반드시 실행되는 프로그램.”

AGENTS.md가 부탁, Rules가 금지라면, Hooks는 자동 집행입니다.

활용 예 — 파일 수정 후 자동 린트 · 프롬프트에 API 키가 들어왔는지 검사 · 턴 종료 시 검증 스크립트 · 대화 로그를 자체 분석 시스템으로 전송 · 대화 요약으로 사용자 정의 영구 메모리 만들기(공식 문서 예시) — Memory 기능을 Hooks로 커스텀 구현할 수도 있다는 점에서, Hooks는 다른 기능들의 빈틈을 코드로 메우는 만능 접착제입니다.

기능 5 / 5 · Hooks 사용법과 제약

hooks.json — 형식 · 위치 · 현재 제약

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command",
            "command": "python3 .codex/hooks/
             check_command_output.py" }
        ]
      }
    ]
  }
}
  • 형식: hooks.json 또는 config.toml의 [hooks]
  • 위치: ~/.codex/hooks.json · ~/.codex/config.toml · <repo>/.codex/hooks.json · <repo>/.codex/config.toml · 플러그인 내부
  • 여러 위치에 일치하는 Hook이 있으면 덮어쓰지 않고 모두 실행 — 프로젝트 로컬 Hook은 해당 .codex/ 계층이 신뢰된 경우에만 로드
  • 현재 제약 — 실제 실행되는 핸들러는 "type": "command"뿐 (prompt·agent 타입과 비동기 옵션은 파싱만 됨)
  • 신뢰되지 않은 Hook은 실행 전 검토·신뢰 절차 필요 (내용 변경 시 해시가 바뀌어 재검토)
  • CLI 관리는 /hooks · 끄려면 [features] hooks = false

my-project/ ├── AGENTS.md # 이 프로젝트에서 항상 알아야 할 사항 ├── .agents/ │ └── skills/ # 반복 호출할 전문 업무 절차 │ ├── run-tests/ │ │ ├── SKILL.md │ │ └── scripts/run-tests.sh │ └── review-pr/ │ ├── SKILL.md │ └── references/review-checklist.md ├── .codex/ │ ├── config.toml │ ├── hooks.json # 언제 어떤 자동화를 실행할지 │ ├── hooks/ # Hook이 실제로 실행하는 코드 │ │ ├── validate_changes.py │ │ └── scan_secrets.py │ └── rules/ │ └── default.rules # 샌드박스 밖 명령의 허용 정책 ├── src/ └── tests/
홈 디렉터리 쪽 구성

내 컴퓨터 전역 설정은 이렇게 정리됩니다

~/.codex/AGENTS.md # 전역 지침 ~/.codex/config.toml # Codex 설정 ~/.codex/hooks.json # 전역 Hook ~/.codex/rules/ # 명령 실행 Rules ~/.codex/memories/ # 자동 생성 Memory (직접 편집 비권장) ~/.agents/skills/ # 개인 Skills (위치가 .codex가 아님에 주의)
한 번 더 — 위치 주의
AGENTS.md·Rules·Hooks·Memory는 ~/.codex/ 아래, Skills만 ~/.agents/skills/ 아래입니다.

Step 1 / 4

작업대를 펴고, 헌법을 쓴다

# ① 프로젝트 폴더를 만들고 작업대를 편다
mkdir my-agent && cd my-agent
git init

# ② 에이전트의 기준점 — AGENTS.md 작성
# AGENTS.md
## 개발 규칙
- 패키지 관리자는 pnpm을 사용한다.
- API 응답 타입에 any를 사용하지 않는다.
## 검증
- 코드 수정 후 pnpm lint / typecheck / test 실행
## 주의사항
- 승인 없이 새 프로덕션 의존성을 추가하지 않는다.
기억하세요
작게 시작해서, 에이전트가 반복해서 틀리는 것을 발견할 때마다 한 줄씩 추가하며 발전시킵니다.
Step 2 / 4

나만의 Skill 하나 만들기

# 저장소 스킬 폴더 생성
mkdir -p .agents/skills/review-pr
# .agents/skills/review-pr/SKILL.md
---
name: review-pr
description: 사용자가 PR 검토, 코드 리뷰, 회귀 분석,
  테스트 누락 검사를 요청할 때 사용
---

1. 변경된 파일 목록을 확인한다.
2. AGENTS.md의 검증 명령(lint / typecheck / test)을 실행한다.
3. 리뷰 결과를 체크리스트로 정리한다.
호출해 보기
앱에서 @review-pr, CLI에서 $review-pr(또는 /skills)로 명시적 호출 — 그리고 “PR 리뷰해줘”라고만 말해 암시적 호출(description 매칭)도 확인해 보세요.
Step 3 / 4

안전장치 달기 — Rules와 Hooks

# .codex/rules/default.rules
prefix_rule(
    pattern = ["rm", "-rf"],
    decision = "forbidden",
    justification = "재귀적 강제 삭제 금지",
)
prefix_rule(
    pattern = ["gh", "pr", "view"],
    decision = "prompt",
    justification = "PR 조회는 승인 후",
)
# .codex/hooks.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command",
            "command":
             "python3 .codex/hooks/check.py" }
        ]
      }
    ]
  }
}
역할 분담을 다시 확인
AGENTS.md에 적은 “위험한 명령 금지”는 부탁 → Rules가 강제로 승격. “수정 후 검증해라”는 부탁 → Hooks가 자동 집행으로 승격.
Step 4 / 4

창고에 올려 팀과 공유한다

# ① 보낼 것을 골라 담고, 봉하고, 보낸다
git add .
git commit -m "에이전트 초기 구성 — AGENTS.md · skill · rules · hooks"
git push

# ② 동료는 창고 주소 하나로 전체를 복원한다
git clone 창고주소
이것이 공유의 힘
동료가 clone하는 순간 — AGENTS.md(지침), Skills(절차), Rules(정책), Hooks(자동화)가 전부 함께 복원됩니다. 사람마다 다르게 시키던 에이전트 업무가 팀 표준이 되는 순간입니다. (단, 프로젝트 로컬 Hook·Rules는 신뢰 절차 후 활성화됩니다.)
완성 체크리스트

오늘 만든 것 — 전부 연결됐나요?

  • Node.js LTS — node --version → v22.x.x 이상 (막히면: 터미널 재시작 / RemoteSigned)
  • git — init → add → commit → push 흐름으로 프로젝트가 기록되고 있다
  • AGENTS.md — 항상 지킬 지침이 저장소 루트에 있다 (작게, 32KiB 안에서)
  • Skill — .agents/skills/review-pr/SKILL.md가 명시적·암시적으로 호출된다
  • Rules — rm -rf는 forbidden, 민감 명령은 prompt로 통제된다
  • Hooks — 도구 실행 후 검증 스크립트가 모델 판단과 무관하게 돈다
  • GitHub — push 완료, 동료가 clone으로 같은 에이전트 환경을 재현할 수 있다
